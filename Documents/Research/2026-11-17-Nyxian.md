# Nyxian 实现原理（jailed 设备上的用户态微内核）

来源：emexlab/Nyxian（main 分支，`ProjectNyxian/Nyxian` 会重定向）。以下每条结论后面都写着对应的仓库路径；
没有读到源码的部分标了「推测」。深度笔记在 `Documents/Research/Nyxian/`（README 总览 + surface / trust-and-kext /
process-patches / build-and-run 四篇），那份比本文详细，两者独立读出来，结论在 task port 交接、NSExtension 承载、
syscall 通道这三点上一致。

## 一句话

Nyxian 不是"在 App 里跑编译器和进程"那么简单：它在一台未越狱的 iOS 上伪造了一整套 POSIX 进程环境——
每个"进程"其实是一个 `LiveProcess.appex`（NSExtension）进程，宿主用 Mach 异常消息拿到它们的 task port，
再用一个 Mach 端口上的 syscall 服务器替 guest 回答 `sysctl`/`kill`/`wait4`/`task_for_pid`/`setuid` 这类问题。
硬约束是它**无法拦截 ARM64 的 SVC 指令**（README 自己写明），所以只能在 libsystem 层替换函数，而不是真的做系统调用层虚拟化。

## 分层

| 层 | 位置 | 干什么 |
| --- | --- | --- |
| IDE / 构建 | `Nyxian/LindChain/IDEBuilder`、`LLVM-On-iOS`（emexlab 的 submodule） | 设备内 clang、链接 Mach-O、签名 |
| 宿主 | `Nyxian/LindChain/ProcEnvironment/Server`、`PEProcessManager`、`PELaunchService*` | 每次 spawn 一个 appex、维护 FBProcess 记录、替 guest 收发信号与 wait |
| 微内核 "ksurface" | `Nyxian/LindChain/ProcEnvironment/Surface` | 进程表、信任/签名、syscall 服务器、fs、tty、kext 加载 |
| guest | `LiveProcess.appex` + `Shims/*`（`litehook` 打补丁） | 目标二进制在 appex 进程里跑，libsystem 调用被改道到宿主 |

`Surface/surface.m` 的 `ksurface_kinit()` 就是"开机"：分配 `ksurface` 映射、取签名公钥、初始化互斥锁、
建进程/kext/tty 三棵 radix tree、起 syscall 服务器、注册 handler 表、插入 `kernel_proc_`、初始化 fs 与 keychain。

## 关键机制一：怎么拿到 guest 的 task port

`Surface/sys/compat/handoffep.c` + `Surface/libkern/task_handoff.c`：

1. guest 线程把自己的 `EXC_MASK_BREAKPOINT` 异常端口设成一个新 Mach 端口（`mach_port_construct` + `MPO_INSERT_SEND_RIGHT`）。
2. 通过 `SYS_handoffep` 把这个端口的 **receive right** 交给宿主（宿主在 `sys_need_in_ports(1, MACH_MSG_TYPE_MOVE_RECEIVE)` 里消费）。
3. guest 执行 `brk #1`，内核产生 EXC_BREAKPOINT，把异常消息发给该端口——**消息体里带 faulting task 的 control port 和 thread port**。
4. 宿主收消息后校验 `mach_port_kobject()` 的类型是 `IPC_OTYPE_TASK_CONTROL` / `IPC_OTYPE_THREAD_CONTROL`，
   再用 `pid_for_task()` 对一遍 pid（`handoffep.c` 里也再验一次），然后 `thread_get_state` 把 `pc += 4` 跳过 `brk`，
   回 reply，guest 继续执行；此时宿主手里已经有完整的 task port。
5. `task_normalize()` 把 `mach_task_self()` 的 send refs 降到 2，避免被 reveil 之类的探测工具发现。

这条路径绕过了 `task_for_pid` 的权限检查：task port 不是"要"来的，是内核自己塞进异常消息里的。
所以后面所有 `task_for_pid`/`waittask` 都能成立（`SYS_task_for_pid`、`SYS_waittask`）。

## 关键机制二：进程是怎么"生"出来的

`Shims/posix_spawn.m`（`LIBKERN_PATCH` 替换 `posix_spawn`/`posix_spawnp`）：

1. `realpath` 目标，读 Mach-O 检查 CMS 签名（`LCCheckCodeSignature`）；没签就打开 fd 调 `SYS_sign` 让微内核签，再复查一次，还不行返回 `ENOEXEC`。
2. 解析 `posix_spawn_file_actions_t`（OPEN/CLOSE/DUP2/INHERIT/CHDIR…）和 `FD_CLOEXEC`，生成一份 `PEFileTable`（描述"哪个 fd 映射到子进程的哪个 fd"，含 fileport 传递）。
3. 通过旧的 ServerSession XPC（`environment_proxy_spawn_process_at_path`）把路径、argv、envp、file table、cwd、spawn flags 交给宿主。
4. 宿主 `PEExtension.m` 的 `PESpawnFBProcess`：调私有 API `NSExtension beginExtensionRequestWithInputItems:` 拉起
   `PlugIns/LiveProcess.appex`，把 `PESyscallPort`（syscall 服务器的 send-once right）和 `PEEnvironment`
   （`HOME`/`CFFIXED_USER_HOME` 指到 Nyxian 的 rootfs，`TMPDIR` 指到 `<rootfs>/tmp`）塞进 `NSExtensionItem.userInfo`；
   然后用 `pidForRequestIdentifier:` + RBS 句柄 `registerProcessForAuditToken:` 把它登记成 `FBProcess`，并校验 `audit_token.val[5] == pid`。
5. guest 侧 `Shims/environment.m` 的 `environment_init()`：抬 `RLIMIT_NOFILE`、装 spawn/vfork/application 补丁、
   轮询 `SYS_getppid` 直到宿主登记完成、`task_handoff()`、改写 executable path（`PEOverwriteExecutablePath` 直接改 CFBundle/NSBundle 的 main bundle 缓存槽），
   再从 `SYS_vroot` 给出的 rootfs 加载 `boot/rtpatch`、`DYLD_INSERT_LIBRARIES`，最后 `LCBootstrapMain()`。

要点：**没有真的 exec**。目标 Mach-O 是在 appex 进程里以 LiveContainer 的方式载入并接管（推测：细节在 `LCBootstrap.m`，未读），
所以 `ksurface_proc_t` 的 kinfo_proc 是宿主凭 spawn 参数自己填的（`Surface/proc/spawn.m` 的 `proc_spawn`），
`ppid`/`pid`/`sid`/`pgid`/`p_comm` 全是伪造值，`p_flag` 里还塞了 `P_SYSTEM`（`surface.m` 的 kernel proc）。

## 关键机制三：syscall 虚拟化

`Surface/sys/` 下的 handler 表在 `surface.m` 的 `sys_list[]` 里注册到 syscall 服务器：

- 自有号段（`ksurface_abi.h`）：`SYS_handoffep` 757、`SYS_pectl` 760、`SYS_sign` 761、`SYS_openpty` 762、
  `SYS_loginctl`/`SYS_groupctl` 763/764、`SYS_vroot` 765、`SYS_task_for_pid` 754、`SYS_waittask` 759；
- 复用系统号但换成自有实现：`SYS_getppid`、`SYS_sysctl`、`SYS_sysctlbyname`、`SYS_ioctl`、`SYS_kill`、`SYS_wait4`、
  `SYS_getuid/setuid/setgid/setreuid/...`、`SYS_getsid/setsid/getpgrp/setpgid`。

宿主侧是"用真 API 办完，把结果写回 guest 内存"——`surface.m` 注释里直接写了这个例子：guest 要进程列表时，
宿主替它 `sysctl` 拿 `kinfo_proc` 数组再拷进 guest 的缓冲区。`PEMachPort`/`syscall_server_get_port` 就是这条通道的端口。
`sys_need_in_ports`/`sys_in_ports`/`sys_out_ports` 说明 Mach 端口（fd、fileport、task port）也在这套消息里传。

进程对象本身是自造的：`proc/def.h` 的 `ksurface_proc` 里塞了 `kvobject` 引用计数头、`task_t`、父子契约数组、
BSD 的 `kinfo_proc`、以及 `knyx_proc`（sid/pgid/pidv、login name、附加组、wait4 状态、entitlements）。
`proc/spawn.m` 还实现了 `proc_kill`（对 pid 1 发 SIGTERM/SIGKILL 等于重启整个 userspace）、`proc_reap`/`proc_zombify`
（SIGCHLD + `kProcEventTypeWait4` 事件），也就是把 fork/exit 语义整体搬到用户态。

## 关键机制四：信任与签名（NXT2）

`Surface/trust/`：

- `entitlement.h` 定义了 Nyxian 自己的一套 `PEEntitlementFlags`（get-task-allowed、task-for-pid、process-spawn(-signed-only)、
  platform、platform-root、system-task-ports、load-kext…）和 **NXT2 entitlement** 字符串（`platform`、`platform-root`、
  `sandbox-host`、`launch-services-*`…）；`proc_spawn` 里把 `platform-root` 直接翻译成 ruid/euid/svuid = 0。
- NXT2 blob 的结构（`ksurface_nxt2_blob_header`）：`cdhash[20] + nonce(8) + plist_len + plist_data` 是**被签名**的部分，
  `footer{mac_len, mac[72]}` 只承载签名身份；安装时生成一对 key（`ksurface_kinit_get_keys` → `get_static_kernel_key`），
  `SYS_sign` 让环境自己给二进制签名，`needsResign` 表示整个二进制要重签。
- `apple.c`/`cdhash.c`/`signing.c`/`summary.m` 负责 Apple CodeDirectory 的解析与 CDHash 计算、与 NXT2 blob 互译。
- `SYS_vroot` 告诉 guest "宿主的根在哪"——guest 里所有绝对路径都要按这个根解释，这是 `NXT2 sandbox-*` 之外的另一半机制。
- kext：`SYS_pectl(kPECTLCodeSigningLoadKernelExtension)` → `ProcEnvironment/KextLoader`，用户态做 kxld 那一套
  （校验签名、加载、fixup、跑 initializer、看 `kmod_info_t`）。

## 和 Apelin 的对照（只列结构差异，不评价）

| 维度 | Nyxian | Apelin |
| --- | --- | --- |
| 前提 | 未越狱，只有证书签名的 App 权限 | roothide/rootless 越狱，`apelind` 以 root 由 launchd 拉起 |
| 进程 | 伪造：appex + 用户态内核，pid/ppid/sid 都是编的 | 真进程：`posix_spawn`/launchd，pid 是真的 |
| 能力来源 | Mach 异常端口骗到的 task port + libsystem 替换 | 真实 root 与会话宿主的认证握手 |
| 签名 | 自建 NXT2 签名体系 + trust store，`SYS_sign` 自签 | 系统 `ldid`/amfid 链路；包要过 dpkg/Irisin |
| 路径 | `SYS_vroot` 把 rootfs 根下发给 guest | 编译期 `@PREFIX@`/`@ROOTFS@`，运行时 `jbroot()` |
| 拦截 | 无法拦 SVC，只能 hook libsystem | 可直接 MSHookMessageEx 对系统进程注入 |
| 交付物 | IPA + 证书 | .deb / .ipa |

可以借鉴的两点（仅作参考，不必据此改架构）：
一是它把"我信任谁"做成了可序列化的 entitlement blob（cdhash+plist 一起签、footer 只放身份），
这与 Apelin 的 `IrisinCodeSign`/`ldid` 摘要校验是同一类问题；
二是它对 guest 的路径根（`SYS_vroot`）与 Apelin 的 `@PREFIX@`/`jbroot()` 面对的是同一个麻烦——
rootfs 会搬家，路径绝不能写死。
